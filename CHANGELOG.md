## [Unreleased]

### Added

- The canvas's look as a design system every platform shares, none of it on screen yet (#142). Two new targets of the root package hold it, neither depending on the core, because the look must not know the domain, and both are tested on the host and on wasm32; a feature module may import both to build the models of its screen's components (ADR-0007, amendment of 2026-10-26). `DesignSystem` holds the design decisions, each a static member or a case of its own type: `DesignSystem.Color` the paper, surface, sidebar, fill, line, three inks, red, accent and accent soft, each a light and a dark shade in sRGB, and under `DesignSystem.Color.Components` the colours of the components, first `Tile`, a list's tile's eleven colours by the names the store keeps, which a root test holds to the core's `TaskViewColor`, each a background and a glyph colour drawn from a base nothing outside sees by the canvas's `paint` rule and not 22 more literals; `DesignSystem.Font` the type as text styles, so that it grows with Dynamic Type, at the canvas's sizes at the iPhone's default text size but for the large title's 34 pt and the meta's 12, with a row's title as four plain fonts, the body and the callout each regular or semibold; `DesignSystem.Animation` the motions, each a curve, a duration and a delay; and `DesignSystem.Icon` the icons by the names the store keeps, a name this app does not know reading as none, with the default glyph, `bullets`, a case of its own, so that no icon is optional. `DesignSystemComponents` holds the models of the components every platform draws, first `TileModel`, a list's tile with every visual parameter a platform needs, plain data with no colour logic: its tile colour, its glyph's icon and its sizes, which its caller gives, and its glyph's medium weight. `TodoAppleUI` holds only the renderers: `Color(_:)` follows the appearance through `UIColor`'s provider on iOS and `NSColor`'s on the Mac and stands at the dark shade on watchOS, which has neither, the one platform condition; `Font(_:)` and `Animation(_:)`; `Image(_:)` draws each icon as an SF Symbol looked up in the system's availability list for iOS 17, macOS 14 and watchOS 10, the default glyph's as `list.bullet`; and `ListTile` draws a `TileModel` in its colour's background and glyph colour, with circular corners. Their callers come in the plan's later tasks: the sidebar's module builds each row's tile and chooses its title's font, reading a view's colour and icon as the design system's by name, the stone colour and the bullets icon for none or a name it does not know (Task 5), and the Lists screen's rows and sidebar draw them (Tasks 7 and 8).

- A view's kind, colour and icon, and the device's own state, in the core (#143). `TaskView` carries `kind`, a `TaskViewKind` of `list` or `area`, `color`, one of the eleven names of `TaskViewColor` or none, and `icon`, the name of a glyph as text or none, and `NewTaskView` takes the three, which `createView` writes with the rest of the view's fields under one stamp. `createView` refuses an area under a parent with "an area cannot be nested" and an area with a filter with "an area has no rule", and `move(view:to:at:)` refuses to move an area under any view with the first sentence. A stored `area` reads as an area only at the root with no filter and as a list anywhere else, an unknown kind or colour reads as absent, an icon reads as its text, and a view written before the fields reads as a plain list. The seed gives the built-ins the canvas's tiles at clock zero, tray on blue for the Inbox, the sun on amber for Today, the calendar on rose for Upcoming, the logbook on green and the bin on stone, and a store an earlier version seeded shows them at its next open; the seed and `createView` write a view through one list of fields. `Store.setDeviceState(_:_:)` keeps a value of a module's own `Codable` type under a key, as JSON written by the encoder the filters use, in a `device_state` table outside the journal: never journaled, never synced, never reported through `onChange`, and carried by a snapshot, since it is the file's (ADR-0010, and its amendment of 2026-10-26 from the owner's review). `deviceState(_:as:)` reads it back as that type; a value that is not text, that nests deeper than the core reads or that does not decode as the type reads as nothing kept, and a value the store could not read back is refused at the write. Schema version 5 adds the three nullable columns and the table, and `FieldMap` knows the three fields, so the operations on them that an M3 build journaled and could not apply are replayed at its first open by this version.

- The counts of the Lists screen and the deletion of a list with everything under it, in the core (#144). `Store.taskCounts(today:)` answers in one call the number of open tasks each view selects, the default a list's row draws beside its title (spec section 4): a list with a rule counts the tasks it selects that are open and not in the trash, by conditions of the count's own over the rule compiled bare, so the Logbook and the Trash count nothing; a list with no rule counts the union of its children, each task once and a folder inside it folded in the same way, as one statement over the disjunction of their conditions, built from the leaves up in one pass over the tree order reversed that never recurses, so no ids travel between statements; the expression is as deep as the tree, and SQLite's recursion over it is #152; an area, a view this app cannot read and a folder with nothing to count have no count, a zero is a count, and the unreadable view adds nothing to the folder above it. Every view with a count costs one statement, which `Store.countStatement(where:)` assembles beside `viewStatement` so that a test explains its plan: the built-ins' counts are driven by the open tasks over the status index, and the Trash's by the partial trash index. `Store.delete(viewTree:)` tombstones a view and every view under it, the subtree as `views()` reads it, with one operation per view under one stamp in one transaction, where `delete(view:)` tombstones one and lets its children surface; the tasks are untouched. Their callers come in the plan's later tasks: the sidebar's module reads the counts beside its rows at every reread (Task 5), and the confirmation of a list's deletion deletes its tree (Task 6).

- ADR-0009 (every screen is a child of the screen that opened it, held in a seat; a screen has a route with a head and a tail, applied through one entrance that reconciles by head; the route of a window has one text form, which is the link, the restored state and the web route; a window is a tree of modules with its own host, a process is one store fanning its changes to every window; a module never writes in answer to `.changed`), extracted from the navigation spec.

- The shared form of a parent, beside the module contract in the `FeatureModule` target, which depends on nothing (#89). `Routable` is the protocol of a module that can be opened: it reports the `route` it is on, assembled from its state, and has an `Event` that is a `RoutedEvent`, spelling `.route(_:)` and `.created` beside `action(_:)`, so that a parent sends both without knowing which module it holds; a route is a `RouteValue` with a head, and `NoHead` is the head of a screen of which there is one. The protocol requires no `init`: each module keeps its own, taking its route and whatever it needs, the store for one screen and nothing for another, and that `init` is where a screen that cannot read what it shows refuses to be made. `Seat` is the generic value a parent holds a child in, so that what a parent wrote ten lines for in M2 is one call. The parent builds it once with the way to make the child, a closure over the child's own `init` that captures the child's dependencies and never the parent, whose error type is the seat's: `StoreError` for a screen that reads the store, and `Never` for one that cannot fail, whose seat is applied without `try`. So the contract names no dependency, and the `FeatureModule` target does not depend on `TodoCore` after all: the owner's review of #100 withdrew that, which an amendment of ADR-0007 of 2026-10-15 and the text of ADR-0009 record. The seat makes the child from a route, tells it it was created and hands back its answer, keeps it and hands it `.route` when the head is the same, replaces it when the head differs, drops it on a nil route, and makes a new child before letting the old one go, so that a child that cannot be made leaves the seat holding what it held. Its tests run over a stub child with no store in a new `FeatureModuleTests` target, because no parent holds a seat until the task list does (#90). It drops them differently, because the two interruptions are not the same: a highlight goes silently, since a person whose highlight moved was not interrupted, while a rename goes with the same sentence a refused write gives for that view, since a peer's delete is that fact arriving by another route and a field vanishing mid-word with no explanation is barely better than the row vanishing. What the store refuses becomes a finished sentence in the model and never a `StoreError`: a view deleted under an open rename is named by its title, while every other refusal reads as the general sentence, because calling a SQLite error "the view is gone" would put on screen something that is not true. What a read that failed means is the caller's to say rather than the read's, so a refusal that named a view keeps its sentence instead of losing it to a general one, and a folder written but not yet readable moves neither the highlight nor the field onto it, and is not reported as chosen either, since the root builds its detail from that alone: what this module puts on a row of its own accord, after a write of its own, goes onto a row the list holds, which is what stops a field opening on a folder made minutes ago the next time an unrelated edit brings its row in. A sentence survives a `.changed`, since what another device did is no answer to what a person did and a problem cleared by a peer's edit would vanish between being read and being acted on, and it is cleared by the next action the module acts on; an action it ignores leaves the model alone, the sentence included, because the field that closed behind a refusal sends its cancellation right after it. The default title is English here and its localisation belongs with the formatting service of M3, and nothing sends `titleFieldLostFocus` until the views of Task 5.
- The module contract and the sidebar's read path. `FeatureModule` is the protocol every feature's logic conforms to — a class holding the `Model` a view draws, taking one `Event` at its single entrance and answering the `Output` its parent acts on — and `FeatureEvent` carries the static `action(_:)` that lets a host lift what a view sent into an event without knowing which module it holds, which is what allows a view to be given a closure over `UserAction` alone: the closure it has cannot spell `.changed`. `TaskViewList` is the first module over that contract, named for the views it holds and not for where it is drawn: the same list is a sidebar beside a Mac window and a screen of its own on a phone. It reads the tree of views out of the store into flat rows of an id, a title, a depth and whether the row is selected, so that a view indents by a number and decides nothing, and the walk that builds them passes `views()` once and takes each row's depth from its parent's, because a chain a thousand deep arrives from sync as easily as a shallow one and the wasm32 stack is 64 KiB. The Inbox is selected at first; choosing a row moves the highlight and answers `.selected(id)` every time, the row already chosen included, since what a second choice of it means is the root's and not the sidebar's; a `ChangeSet` that names a view rereads the whole tree, because views number in the tens and the tree order needs every row anyway, while one that names none costs not even a read, which is what every edit to a task is. A selected view a peer deleted leaves no row selected and answers nothing, because a deletion elsewhere is not a choice anybody made. `init` throws, since a store that cannot be read at launch is the composition root's to refuse rather than a sidebar that comes up looking like an empty database, and `send` never throws: a read that fails inside it keeps the rows on screen and writes into `model.problem` a finished sentence, composed by the module from a typed problem of its own, which the view shows until the next event and draws nothing in place of when there is none. The store's error stays inside the module: it names SQLite codes and journal rows, which is what a bug report is made of and not what a person reads. The manifest gains targets and no product: one target per feature, `TaskViewListFeature` at `Sources/Features/TaskViewList`, is what makes `internal` mean "inside this feature" and puts the dependency graph where a review reads it, and the products go in with the Apple package that imports them. The test helpers moved to a `TestSupport` target under `Tests/Support`, ordinary and not a test target because a test target cannot be depended on, so that the core's tests and every feature's open a store the same way; it is in no product and nothing ships it.
- Implementation plan `docs/plans/feature-module-architecture.md`, the first written from `docs/plans/TEMPLATE.md`: six tasks, the module contract and the sidebar's read path, the sidebar's writes, the root module and the size probe that drives it, the Apple package with the host and the composition root, the views and the executable, and CI with the documentation that closes the epic. - The `todo` command-line demo over a `TodoCLI` library target: `add`, `list`, `views`, `view add`, `show`, `done`, `cancel`, `reopen`, `edit`, `move`, `tag`, `untag`, `pin`, `unpin`, `trash`, `restore`, `delete` and `find`, each going through the public API of `TodoCore` and printing one fact per line, so that a person reads the answer and a script cuts it. A newline inside a title, a tag name or a snippet becomes a space on those lines, because a title arrives from a person and from sync alike and one that held a newline would leave the id of a task on a line of its own. A task is named by any prefix of its id that names a single task, and a prefix that names two is refused with the count rather than acted on; a view is named by its title or by an id prefix, and a title that two views share is refused the same way, since answering with whichever row the read returned first would send `list` and `pin` to different lists on two runs of one command. Every option a command does not take is refused by name, and so is an option with no value, another option where its value should be, or a word left after one, which is what an unquoted `--notes before the review` looks like once the shell has split it: taking `before` for the note and joining `the review` into the title is the kind of silence a demo cannot afford. The database is `todo.sqlite` in the working directory, `TODO_DB` and then `--db PATH` override it, `TODO_TODAY` says what day the query is made on, and a variable exported without a value reads as unset rather than stopping every command; a command the demo refuses exits 2 and one the core refuses exits 1. The commands live in a library target and are tested against an in-memory store on the host and on wasm32, the way the core is, and the executable is one line. `Store.systemNow` is the wall clock that line passes in: the core still takes its clock from the caller and holds no policy about it, and a machine whose clock is set far enough ahead, or one that answers with nothing at all, saturates the conversion rather than trapping it. What it answers is the time of day on every target the app ships on, wasm in a browser among them, where the JS host that stands in for WASI answers the realtime clock with `Date.now()`; the one host that reads the machine's uptime instead is the WasmKit the toolchain carries, which is the test runner and not a device, so no test on wasm32 asserts a real wall-clock value and what that runner answers instead is held as a bound by a test, which fails on the first host that tells the truth (#53).

- The sync skeleton of the `TodoCore` store: `Store.journal(after:)`, which exports the journal in the order this device wrote it — operations and not rows, because the sequence number that orders them is this store's own counting and means nothing on another device; `Store.receive`, which takes another device's operations through the same path a local edit takes, after this device's clock has observed their stamps, so an edit made in answer to what arrived sorts after it and wins; `SyncTransport` with `InMemoryRelay`, the two-action transport the spec asks for and the only implementation in M1; and `SyncEngine.sync`, one round of push and pull whose two cursors live in `meta` — the pushed one a local sequence number, the pulled one the transport's — so a restart resumes where the last round stopped and a page the transport has already taken is not offered again, even when the pull of that same round fails. The push walks the journal by the row its scan reached and not by the last row it could decode, because those are different numbers: a row naming an entity kind a newer version of the app wrote is stepped over, and a cursor that stopped at a page of them would stop the device from ever pushing its own later edits. Two stores whose wall clocks are five seconds apart converge after concurrent edits to the same task: the later edit wins per field, an edit to another field of it survives alongside, and structure, tags, views, manual lists, trash and deletion all cross. Operations this device wrote are dropped as they come back — a transport hands back what it was given, and the journal's unique index and the field clocks would only drop them again, one statement at a time. What a peer sent and the state could not hold is counted instead of hidden: a null for a NOT NULL column, an id that names no entity at all, or a pair id that does not split is journaled, skipped and reported by `receive` as `refused`, because failing the statement would roll back every operation delivered with it, on this delivery and on every retry after it, and one bad field would stop sync for good. A field this version does not know is not refused and is not counted: it waits in the journal with `applied = 0` for the migration that adds the column.

- Search over the `TodoCore` store: `quickFind`, a substring search over the titles of tasks, tags and views, and `searchNotes`, a ranked word search over notes. Quick find reads the three trigram indexes, which fold case and the diacritics SQLite's own tables cover, so `отч` finds `Квартальный отчёт` and `cafe` finds `Café run` — `ё` is a letter of its own to them and not an `е` with a mark; a query shorter than three characters has no trigram to look up at all, so the titles are scanned in Swift instead, folding case but not diacritics, which is what two characters can honestly answer while the word is still being typed. Hits of all three kinds are ordered by one rule, the title folded by the standard library with the id settling ties, because the order decides which rows the limit keeps: `COLLATE NOCASE`, the only folding SQLite has without ICU, folds the ASCII letters alone, so it would sort a Cyrillic title by its bytes — every capital before every lowercase — and a limited answer would drop the title that comes first in the alphabet a person reads. Tasks are ordered and cut before they are read whole, since the sort needs an id and a title and nothing else: a two-character scan over fifty thousand tasks reads two columns rather than fifty thousand tasks with their tags, 65 ms against 93 ms in a release build, while a trigram query matching twenty of them answers in 0.2 ms. Notes search takes every word but the last as a whole word and the last as a prefix — unless it ends in punctuation, because `C#` is a finished word and a star after it would rank every note holding a word that starts with `c` above the one that mentioned `C#` — orders by `bm25`, which is negative and smaller for a better match and is carried out of the core so that a caller merging two searches can rank across them, and returns a twelve-token snippet with the matched words in square brackets. Whatever a person types reaches FTS5 as a quoted string with its inner quotes doubled, so `OR`, `NOT`, `NEAR` and the quotes themselves are searched for instead of obeyed, and only the ends of a query are trimmed: the index holds a title byte for byte, so collapsing the run of spaces inside `Buy  milk` would leave it unreachable by the text on the screen. Both searches hide trashed and deleted tasks, inherited trash included, and deleted tags and views never appear; the indexes follow a rename or a note edit through the triggers of schema version 1; and a limit of zero or less asks for no room and gets nothing, where `prefix` would trap on a negative one and SQLite would read it as no limit at all. `SQLiteKit.Value` gained the `double` accessor its first caller needed: no column of the schema holds a real, but `bm25` returns one.
- Views and page queries of the `TodoCore` store: `TaskView`, `NewTaskView` and `TaskViewChange` for a view that nests to any depth, carries a filter, a sort and a grouping, and reads its effective parent by the rule the task tree follows, so a link a merge left pointing at a missing, deleted or circular view reads as no link and the view shows at the root; the five built-in views Inbox, Today, Upcoming, Logbook and Trash, seeded at every open with fixed ids from the device `seed` at clock zero, so two devices write byte-identical journal rows instead of racing to create two Inboxes, the second open writes nothing, and every edit or deletion a person makes to one of them outranks the seed and survives; manual lists, where `pin` and `unpin` place a task in a view by a fractional rank and `manualList` reads it back; and `tasks(in:today:)` and `page(of:today:)`, which order the groups of a view by its sort and the tasks inside a group by its manual list — grouping by nothing is one group, so an ungrouped view still puts its pinned tasks first and the flat list of a view is the groups of its own result laid end to end — render each child view as a section in rank order followed by the results no child claimed, and group by `when` day, deadline day, tag, parent or status. A view with no filter is a folder, and a heading inside a project is the same mechanism — a child view whose filter is "listed in this view" — so folders in the sidebar and headings in a list are one thing. A definition this version cannot read, from a newer app or a corrupt row, names what it could not read and is reported as `viewNeedsNewerApp` instead of evaluated, because a filter with a condition dropped is a list missing exactly the rows that condition selected; that covers a filter, sort or grouping column holding something that is not text at all, which read as an empty column would turn the view into a folder showing nothing. Inside a page the report is per section: a child view a newer app wrote draws an empty section that names what it needs, and every sibling still draws, because a folder holds lists that have nothing to do with each other; only opening that view as the page itself is an error. The view entity is `TaskView` and a page's parts are `TaskViewPage.Section` and `TaskViewPage.Group`, for the reason `TodoTask` carries its prefix (#42): a core that exported `View`, `Section` or `TaskGroup` would make every SwiftUI file that imports it fail to compile, and a top-level `TaskGroup` would shadow `_Concurrency.TaskGroup` outright.
- Schema version 2 indexes the trashed rows of `task_tree`, and `QueryTests` checks the query plan of every built-in view with `EXPLAIN QUERY PLAN`, which is the guard the spec's "Cost" paragraph promises: a built-in view that walks a table holding one row per task fails a test instead of surprising a person with a large list. Trash was doing it, because it selects on inherited trash, which lives only in `task_tree`, and version 1 indexed that table by parent alone. The index is partial, over the trashed rows only, and `FilterCompiler` now writes the trash flag into the SQL instead of binding it, which is what lets SQLite see that `= 1` implies the index's own condition; the two belong together, and the flag is a `Bool`, so nothing is injectable. An index over the whole column would instead be usable by the implicit `tt.trashed = 0` that every other view carries, and the planner takes it, driving those joins from the rows that are not trashed — nearly all of them — rather than from the condition the view is about. Measured in a release build at 50,000 tasks with 2,000 done and 20 in the trash: Trash goes from 0.64 ms to 0.066 ms while the Logbook stays at 1.81 ms, where a full index would have cost the Logbook 15.8 ms. The guard covers that failure too, since driving a join from the wrong side reads as a `SEARCH` and not as a scan.
- Filters of the `TodoCore` store: `Filter`, the tree of conditions a view is defined by — status, a `when` or deadline day given as an offset from the day the query is made, a tag, an effective parent, membership of a view's manual list, trash, and `and`, `or` and `not` over all of them — with `DayCondition`, `SortKey`, `SortField` and `GroupBy`, and the JSON format that names every node by `kind` and writes its keys in sorted order, so two devices that save the same filter produce the same bytes and last-write-wins does not compare strings that differ only in key order. `FilterCompiler` turns a filter into one parameterised WHERE fragment over `tasks` joined to `task_tree`, adding the exclusion of trash unless the filter mentions trash itself, and a sort into an ORDER BY that puts tasks without a day at the end in both directions and ends with rank and id so the order is stable; a negation reads an unknown as false first, because SQL's three-valued logic would otherwise drop exactly the tasks with no day and no parent that the negation is there to return. Everything a stored filter carries is treated as arbitrary, since the device that wrote it may be newer, older or wrong: a condition kind, a status, a sort field or a condition whose selecting key a newer app replaced is reported by name instead of being dropped, so a view says it needs a newer app rather than drawing a list that is missing rows; a day offset is computed in 64 bits and saturates, where narrowing it to the width of a day would trap; and a document nested deeper than 32 levels is refused before Foundation walks it, because on the 64 KiB stack of wasm32 both its scanner and its decoder exhaust the stack on a filter a few dozen levels deep, and either death repeats on every read of the view (#34).
- The task and tag API of the `TodoCore` store: creating, editing, trashing, restoring, deleting and moving a task between parents or inside its own list, attaching and detaching tags, the same moves for a tag, and the reads behind them — one task, its notes, the children of a task or of the root, every task, and the tag tree in order. Every write is a list of field operations handed to `apply`, so an edit that touches three fields is one transaction, one stamp and one change set, and nothing in the API writes a row itself; the completion time follows the status instead of the caller, so a task that leaves `open` records when it left and one that returns to it has no completion time at all. Placing an item at the end of a list, at its start or after a sibling computes a fractional rank among the siblings a read shows, so an insert never renumbers the list and a reorder inside one list writes the rank alone, and an order clause falls back to the id where two offline devices computed the same key. Reads take the effective parent and the inherited trash from `task_tree`, and a tag's parent is resolved by the same rule, so a link a merge left pointing at a missing, deleted or circular tag reads as no link and the tag shows at the root; a deleted tag disappears from every task that carried it and a deleted task leaves its children at the root, both by the reading rule rather than by a write that walks the tree.
- The task tree of the `TodoCore` store: `TreeRules`, the one rule that resolves parent links after a merge — a link to a parent that is missing or deleted, or one that closes a cycle, reads as no link and the task shows at the root — and the derived `task_tree` table that carries the effective parent and inherited trash for every task a read has to see. Trash reaches down from a task's effective ancestors, a deleted task leaves the tree and its children move to the root, and a chain hanging off a cycle keeps its parent, so a subtree does not lose its shape over a cycle it merely hangs from. `apply` rebuilds the table when `parent`, `trashed` or `deleted` changes or when an operation brings a task into being, and opening a store rebuilds it from the state, so a database written under older rules is read by the current ones.
- The single write path of the `TodoCore` store: `JournalOperation`, the field-level unit of the journal and of a future sync, `EntityKind` with the map from journal fields to state columns, and `Store.apply`, which journals every operation it is given, applies the ones that win their field clock — last write wins, a tie broken by device id — updates the state row and the entity's `updated_at`, and hands what changed to `onChange` once the transaction has committed. An operation whose field this version of the app does not know is journaled unapplied rather than dropped, so a database written by a newer version keeps those edits until a migration makes the field known and `replayUnapplied` applies them in clock order; the same operation seen twice is journaled once, and a pair of entities (a tag on a task, a task in a manual list) upserts its row and reports both sides as changed.
- Schema version 1 of the `TodoCore` store and the way a store opens: the DDL of every state table with its indexes, the four FTS5 indexes over titles and notes and the triggers that keep them in step, an ordered migration runner keyed on `PRAGMA user_version` that runs each step once inside its own transaction, and `Store` itself with `open`, `openInMemory`, `snapshot`, the `meta` table and a device id minted at first open and kept across a snapshot round trip and a file reopen. A store that opens an existing database first reads the largest stamp its journal holds and carries its hybrid clock past it, so an edit made after a restart cannot land behind a clock the device has already seen and lose the last-write-wins comparison in silence.
- The core value types in `TodoCore`: `EntityID`, which mints a lowercase UUID when constructed without an argument, with its `TaskID`/`TagID`/`ViewID` aliases; `Day`, a time-zone-free calendar day in plain integer arithmetic that parses strict `YYYY-MM-DD` and throws `DayParseError` on anything else; `HLC` with `HybridClock`, whose stamps never go backwards on a device, never fall behind a device they have seen, and borrow the next millisecond instead of overflowing the counter, except at the very top of the encoding, where they saturate; and `Rank`, fractional order keys that insert without renumbering and read a neighbour they cannot use as no neighbour, the way a merge's leftovers are tolerated elsewhere. The `CoreSmoke` placeholder is gone: its SQLite version pin and its Cyrillic trigram check moved to `SQLiteKitTests`, and the rest of what it proved is exercised by the schema from Task 4 on.

Because the vendored build has threads off, the wrapper also performs SQLite's one-time library initialization once before the first connection opens, and the `TodoCore` placeholder now goes through the wrapper instead of the C API.

### Fixed

- Two stores opened from the bytes of one database are two devices. The device id used to be minted at the first open and kept in the database, so a copy — a restored backup, or the snapshot the web target saves and reloads — carried the identity of the machine it came from, and the two live replicas then dropped each other's operations as their own and broke a tie on the clock the same way on both sides: they diverged with no error, no refusal and no report, and no later sync could bring them back together (#51). The identity is the platform's now: `Store.open(path:device:now:)` and `Store.openInMemory(snapshot:device:now:)` take it, the core mints none behind the caller's back, `Store.newDeviceID()` is there for a platform with nowhere better to take one from, and an empty id or `seed`, which belongs to the built-in view rows that every device writes and none pushes, is refused (ADR-0005). Schema version 4 keeps the ids a database has written under in `own_devices` and takes the old `meta.device_id` row into it, because a push has to go on sending what an earlier identity wrote and never managed to deliver — a restored copy would otherwise hold those edits forever, applied to its own state and out of every other device's reach. And `receive` stopped dropping what carries this device's own id, which used to save the journal statement and the field-clock read that an echo of a push costs: an identity that outlives its database can outlive its data as well, and a device that kept its id and lost the database — a deleted file beside a kept one, a page whose IndexedDB was cleared while `localStorage` was not — would never see a single row it had written again. What the store already holds is refused by the unique index and by the field clock and moves nothing; a copy takes the edits of the machine it came from the same way, under the id it inherited. The demo keeps its id in `<database>.device` beside the database, which `TODO_DEVICE` overrides, so copying `todo.sqlite` on its own gives the copy an identity of its own.

- Search reads `ё` and `е` as one letter. SQLite's own folding tables cover the Latin ranges, so both tokenizers indexed `ё` as a letter of its own and a person who typed `отчет` did not find `Квартальный отчёт`, in a title or in a note, while the spec promises a search that is insensitive to case and marks in Russian as well as English. Schema version 3 gives every indexed column a generated copy with the pair collapsed, rebuilds the four FTS5 indexes over the copies and rewrites the nine triggers to write them; the copies are `VIRTUAL`, so they cost nothing on disk, and `PRAGMA table_info` does not list them, which is why the journal's field map neither writes them nor has to learn they exist. `Store.folded` collapses the query text by the same rule and walks unicode scalars, because the column is written with `replace`: Swift compares by canonical equivalence and would fold an `е` that carries a combining diaeresis, which SQLite leaves alone, so a test holds the two rules to each other on exactly that text. A tokenizer of our own, registered through the fts5 API, would have folded inside the index and left the columns alone, but it puts C in a core that is Swift (ADR-0001) and makes the file unusable without it — these triggers run on every write, so an ordinary `INSERT INTO tasks` from `sqlite3` would be refused; indexing folded text while telling fts5 that the content is the original needs no column at all and is a trap for whoever comes next, since `'rebuild'` silently replaces the folded index with an unfolded one and `'integrity-check'` answers `fts5: checksum mismatch`. Because the index now reads the copy, `snippet()` speaks folded text: `searchNotes` asks fts5 for the window twice, once marked and once plain, finds the plain window in the folded copy with `instr` and cuts the same span out of the notes with `substr` — one character replaced by one character leaves every position where it was — so a person reads their own spelling back and the notes, which the spec allows to be megabytes, never leave SQLite (#47).
- The unit of the journal of `TodoCore` is `JournalOperation`, not `Operation`. `Operation` is Foundation's `NSOperation`, which every Apple consumer gets through Foundation and through SwiftUI, and `SyncTransport` is the first public API of the core that makes a consumer write the name in its own code: an unqualified `Operation` in a file that imports both is ambiguous for type lookup — an error at each use naming both candidates, not a shadowing that still compiles — so the consumer cannot spell the type without qualifying it. Nothing inside the core noticed, because the core imports neither Foundation nor SwiftUI. `EntityKind`, `FieldMap` and the tables keep their names, and a test now holds the new one the way the guard for `TodoTask` holds its own, reading the declared name through reflection, so that the guard cannot be satisfied by aliasing the new name onto an `Operation` left exported under it. `docs/style.md` names this third case under the rule it already carries (#49).
- The task entity of `TodoCore` is `TodoTask`, not `Task`. An unqualified `Task` in a module that imports the core resolved to the entity and hid `_Concurrency.Task`, so every consumer that used structured concurrency would have had to qualify it; a test that spells `Task<Void, Never>` from a consumer's point of view now guards the name. `TaskID`, `TaskStatus`, `NewTask` and `TaskChange` keep their names, and the plan's later tasks name the new type (#42).
- A stamp at the end of the hybrid clock's range no longer aborts the process. `HybridClock` saturates at the largest stamp the encoding holds instead of borrowing a millisecond outside it, and pulls the wall-clock reading into that range as well, so neither a journal row, nor an operation from another device, nor a system clock set past the end of time can reach the initializer's precondition and kill every later edit on the device. What saturation costs is written in the type: at the ceiling stamps stop being unique, so last-write-wins falls back to the device-id tie-break. Opening a store no longer bounds its own journal scan against the same trap, so the rule lives in the clock alone, where a future `receive` from the transport meets it too.
