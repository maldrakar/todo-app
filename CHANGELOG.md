# Changelog

All notable changes to this project are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Version numbers follow the milestone numbering described in `docs/process.md`.

## [Unreleased]

### Added

- The sync skeleton of the `TodoCore` store: `JournalEntry` with `Store.journal(after:)`, which exports the journal in the order this device wrote it; `Store.receive`, which takes another device's operations through the same path a local edit takes, after this device's clock has observed their stamps, so an edit made in answer to what arrived sorts after it and wins; `SyncTransport` with `InMemoryRelay`, the two-action transport the spec asks for and the only implementation in M1; and `SyncEngine.sync`, one round of push and pull whose two cursors live in `meta` — the pushed one a local sequence number, the pulled one the transport's — so a restart resumes where the last round stopped and a page the transport has already taken is not offered again, even when the pull of that same round fails. The push walks the journal by the row its scan reached and not by the last row it could decode, because those are different numbers: a row naming an entity kind a newer version of the app wrote is stepped over, and a cursor that stopped at a page of them would stop the device from ever pushing its own later edits. Two stores whose wall clocks are five seconds apart converge after concurrent edits to the same task: the later edit wins per field, an edit to another field of it survives alongside, and structure, tags, views, manual lists, trash and deletion all cross. Operations this device wrote are dropped as they come back — a transport hands back what it was given, and the journal's unique index and the field clocks would only drop them again, one statement at a time. What a peer sent and the state could not hold is counted instead of hidden: a null for a NOT NULL column, an id that names no entity at all, or a pair id that does not split is journaled, skipped and reported by `receive` as `refused`, because failing the statement would roll back every operation delivered with it, on this delivery and on every retry after it, and one bad field would stop sync for good. A field this version does not know is not refused and is not counted: it waits in the journal with `applied = 0` for the migration that adds the column.

- Search over the `TodoCore` store: `quickFind`, a substring search over the titles of tasks, tags and views, and `searchNotes`, a ranked word search over notes. Quick find reads the three trigram indexes, which fold case and the diacritics SQLite's own tables cover, so `отч` finds `Квартальный отчёт` and `cafe` finds `Café run` — `ё` is a letter of its own to them and not an `е` with a mark; a query shorter than three characters has no trigram to look up at all, so the titles are scanned in Swift instead, folding case but not diacritics, which is what two characters can honestly answer while the word is still being typed. Hits of all three kinds are ordered by one rule, the title folded by the standard library with the id settling ties, because the order decides which rows the limit keeps: `COLLATE NOCASE`, the only folding SQLite has without ICU, folds the ASCII letters alone, so it would sort a Cyrillic title by its bytes — every capital before every lowercase — and a limited answer would drop the title that comes first in the alphabet a person reads. Tasks are ordered and cut before they are read whole, since the sort needs an id and a title and nothing else: a two-character scan over fifty thousand tasks reads two columns rather than fifty thousand tasks with their tags, 65 ms against 93 ms in a release build, while a trigram query matching twenty of them answers in 0.2 ms. Notes search takes every word but the last as a whole word and the last as a prefix — unless it ends in punctuation, because `C#` is a finished word and a star after it would rank every note holding a word that starts with `c` above the one that mentioned `C#` — orders by `bm25`, which is negative and smaller for a better match and is carried out of the core so that a caller merging two searches can rank across them, and returns a twelve-token snippet with the matched words in square brackets. Whatever a person types reaches FTS5 as a quoted string with its inner quotes doubled, so `OR`, `NOT`, `NEAR` and the quotes themselves are searched for instead of obeyed, and only the ends of a query are trimmed: the index holds a title byte for byte, so collapsing the run of spaces inside `Buy  milk` would leave it unreachable by the text on the screen. Both searches hide trashed and deleted tasks, inherited trash included, and deleted tags and views never appear; the indexes follow a rename or a note edit through the triggers of schema version 1; and a limit of zero or less asks for no room and gets nothing, where `prefix` would trap on a negative one and SQLite would read it as no limit at all. `SQLiteKit.Value` gained the `double` accessor its first caller needed: no column of the schema holds a real, but `bm25` returns one.
- Views and page queries of the `TodoCore` store: `TaskView`, `NewTaskView` and `TaskViewChange` for a view that nests to any depth, carries a filter, a sort and a grouping, and reads its effective parent by the rule the task tree follows, so a link a merge left pointing at a missing, deleted or circular view reads as no link and the view shows at the root; the five built-in views Inbox, Today, Upcoming, Logbook and Trash, seeded at every open with fixed ids from the device `seed` at clock zero, so two devices write byte-identical journal rows instead of racing to create two Inboxes, the second open writes nothing, and every edit or deletion a person makes to one of them outranks the seed and survives; manual lists, where `pin` and `unpin` place a task in a view by a fractional rank and `manualList` reads it back; and `tasks(in:today:)` and `page(of:today:)`, which order the groups of a view by its sort and the tasks inside a group by its manual list — grouping by nothing is one group, so an ungrouped view still puts its pinned tasks first and the flat list of a view is the groups of its own result laid end to end — render each child view as a section in rank order followed by the results no child claimed, and group by `when` day, deadline day, tag, parent or status. A view with no filter is a folder, and a heading inside a project is the same mechanism — a child view whose filter is "listed in this view" — so folders in the sidebar and headings in a list are one thing. A definition this version cannot read, from a newer app or a corrupt row, names what it could not read and is reported as `viewNeedsNewerApp` instead of evaluated, because a filter with a condition dropped is a list missing exactly the rows that condition selected; that covers a filter, sort or grouping column holding something that is not text at all, which read as an empty column would turn the view into a folder showing nothing. Inside a page the report is per section: a child view a newer app wrote draws an empty section that names what it needs, and every sibling still draws, because a folder holds lists that have nothing to do with each other; only opening that view as the page itself is an error. The view entity is `TaskView` and a page's parts are `TaskViewPage.Section` and `TaskViewPage.Group`, for the reason `TodoTask` carries its prefix (#42): a core that exported `View`, `Section` or `TaskGroup` would make every SwiftUI file that imports it fail to compile, and a top-level `TaskGroup` would shadow `_Concurrency.TaskGroup` outright.
- Schema version 2 indexes the trashed rows of `task_tree`, and `QueryTests` checks the query plan of every built-in view with `EXPLAIN QUERY PLAN`, which is the guard the spec's "Cost" paragraph promises: a built-in view that walks a table holding one row per task fails a test instead of surprising a person with a large list. Trash was doing it, because it selects on inherited trash, which lives only in `task_tree`, and version 1 indexed that table by parent alone. The index is partial, over the trashed rows only, and `FilterCompiler` now writes the trash flag into the SQL instead of binding it, which is what lets SQLite see that `= 1` implies the index's own condition; the two belong together, and the flag is a `Bool`, so nothing is injectable. An index over the whole column would instead be usable by the implicit `tt.trashed = 0` that every other view carries, and the planner takes it, driving those joins from the rows that are not trashed — nearly all of them — rather than from the condition the view is about. Measured in a release build at 50,000 tasks with 2,000 done and 20 in the trash: Trash goes from 0.64 ms to 0.066 ms while the Logbook stays at 1.81 ms, where a full index would have cost the Logbook 15.8 ms. The guard covers that failure too, since driving a join from the wrong side reads as a `SEARCH` and not as a scan.
- Filters of the `TodoCore` store: `Filter`, the tree of conditions a view is defined by — status, a `when` or deadline day given as an offset from the day the query is made, a tag, an effective parent, membership of a view's manual list, trash, and `and`, `or` and `not` over all of them — with `DayCondition`, `SortKey`, `SortField` and `GroupBy`, and the JSON format that names every node by `kind` and writes its keys in sorted order, so two devices that save the same filter produce the same bytes and last-write-wins does not compare strings that differ only in key order. `FilterCompiler` turns a filter into one parameterised WHERE fragment over `tasks` joined to `task_tree`, adding the exclusion of trash unless the filter mentions trash itself, and a sort into an ORDER BY that puts tasks without a day at the end in both directions and ends with rank and id so the order is stable; a negation reads an unknown as false first, because SQL's three-valued logic would otherwise drop exactly the tasks with no day and no parent that the negation is there to return. Everything a stored filter carries is treated as arbitrary, since the device that wrote it may be newer, older or wrong: a condition kind, a status, a sort field or a condition whose selecting key a newer app replaced is reported by name instead of being dropped, so a view says it needs a newer app rather than drawing a list that is missing rows; a day offset is computed in 64 bits and saturates, where narrowing it to the width of a day would trap; and a document nested deeper than 32 levels is refused before Foundation walks it, because on the 64 KiB stack of wasm32 both its scanner and its decoder exhaust the stack on a filter a few dozen levels deep, and either death repeats on every read of the view (#34).
- The task and tag API of the `TodoCore` store: creating, editing, trashing, restoring, deleting and moving a task between parents or inside its own list, attaching and detaching tags, the same moves for a tag, and the reads behind them — one task, its notes, the children of a task or of the root, every task, and the tag tree in order. Every write is a list of field operations handed to `apply`, so an edit that touches three fields is one transaction, one stamp and one change set, and nothing in the API writes a row itself; the completion time follows the status instead of the caller, so a task that leaves `open` records when it left and one that returns to it has no completion time at all. Placing an item at the end of a list, at its start or after a sibling computes a fractional rank among the siblings a read shows, so an insert never renumbers the list and a reorder inside one list writes the rank alone, and an order clause falls back to the id where two offline devices computed the same key. Reads take the effective parent and the inherited trash from `task_tree`, and a tag's parent is resolved by the same rule, so a link a merge left pointing at a missing, deleted or circular tag reads as no link and the tag shows at the root; a deleted tag disappears from every task that carried it and a deleted task leaves its children at the root, both by the reading rule rather than by a write that walks the tree.
- The task tree of the `TodoCore` store: `TreeRules`, the one rule that resolves parent links after a merge — a link to a parent that is missing or deleted, or one that closes a cycle, reads as no link and the task shows at the root — and the derived `task_tree` table that carries the effective parent and inherited trash for every task a read has to see. Trash reaches down from a task's effective ancestors, a deleted task leaves the tree and its children move to the root, and a chain hanging off a cycle keeps its parent, so a subtree does not lose its shape over a cycle it merely hangs from. `apply` rebuilds the table when `parent`, `trashed` or `deleted` changes or when an operation brings a task into being, and opening a store rebuilds it from the state, so a database written under older rules is read by the current ones.
- The single write path of the `TodoCore` store: `Operation`, the field-level unit of the journal and of a future sync, `EntityKind` with the map from journal fields to state columns, and `Store.apply`, which journals every operation it is given, applies the ones that win their field clock — last write wins, a tie broken by device id — updates the state row and the entity's `updated_at`, and hands what changed to `onChange` once the transaction has committed. An operation whose field this version of the app does not know is journaled unapplied rather than dropped, so a database written by a newer version keeps those edits until a migration makes the field known and `replayUnapplied` applies them in clock order; the same operation seen twice is journaled once, and a pair of entities (a tag on a task, a task in a manual list) upserts its row and reports both sides as changed.
- Schema version 1 of the `TodoCore` store and the way a store opens: the DDL of every state table with its indexes, the four FTS5 indexes over titles and notes and the triggers that keep them in step, an ordered migration runner keyed on `PRAGMA user_version` that runs each step once inside its own transaction, and `Store` itself with `open`, `openInMemory`, `snapshot`, the `meta` table and a device id minted at first open and kept across a snapshot round trip and a file reopen. A store that opens an existing database first reads the largest stamp its journal holds and carries its hybrid clock past it, so an edit made after a restart cannot land behind a clock the device has already seen and lose the last-write-wins comparison in silence.
- The core value types in `TodoCore`: `EntityID`, which mints a lowercase UUID when constructed without an argument, with its `TaskID`/`TagID`/`ViewID` aliases; `Day`, a time-zone-free calendar day in plain integer arithmetic that parses strict `YYYY-MM-DD` and throws `DayParseError` on anything else; `HLC` with `HybridClock`, whose stamps never go backwards on a device, never fall behind a device they have seen, and borrow the next millisecond instead of overflowing the counter, except at the very top of the encoding, where they saturate; and `Rank`, fractional order keys that insert without renumbering and read a neighbour they cannot use as no neighbour, the way a merge's leftovers are tolerated elsewhere. The `CoreSmoke` placeholder is gone: its SQLite version pin and its Cyrillic trigram check moved to `SQLiteKitTests`, and the rest of what it proved is exercised by the schema from Task 4 on.
- `SQLiteKit`, a typed wrapper over the vendored SQLite: `Connection`, `Statement`, `Value` and `SQLiteError` with typed throws, transactions, user version, `lastInsertRowID`, `changes` and the snapshot pair `serialize`/`deserialize`. Because the vendored build has threads off, the wrapper also performs SQLite's one-time library initialization once before the first connection opens, and the `TodoCore` placeholder now goes through the wrapper instead of the C API.
- Package skeleton for the `TodoCore` SwiftPM package: vendored SQLite 3.53.4 amalgamation as the `CSQLite` target with its provenance and upgrade steps recorded in `Sources/CSQLite/README.md`, placeholder `SQLiteKit`/`TodoCore`/`todo` targets, smoke tests proving UUID, timers and FTS5 trigram search work on both the host and wasm32 under WasmKit, and the Linux CI job that runs them.
- Implementation plan `docs/plans/core-storage-and-search.md`: thirteen tasks that became sub-issues #11 to #23 of epic #4. ADR-0002 (vendored SQLite), ADR-0003 (operation journal with last-write-wins per field) and ADR-0004 (flat model with filter-defined views) extracted from the spec.
- Spec `docs/specs/core-storage-and-search.md`, approved by the owner on 2026-09-11: local-first core with an operation journal for a future sync, vendored SQLite on every platform, a flat model of tasks, tags and nested views with filters, FTS5 search over titles and notes.
- ADR-0001: the core is full Swift on the standard library and FoundationEssentials, replacing the brief's Embedded Swift requirement after the toolchain spike (#3). `.swift-version` pins Swift 6.3.3 for swiftly.

### Changed

- `docs/style.md` records the naming rule the owner's reviews have now set twice: a type the core exports never takes a name a module its consumers import already owns. The collision is invisible inside the core, which imports neither SwiftUI nor anything that defines `Task`, and costs every file in the app. A candidate is settled by a compiler probe against the real modules, and the name a consumer needs is held by a test that spells it (#42, PR #46).
- The spec's table of built-in views says what the core ships: Today sorts by `when`, so what is overdue comes first, and the Logbook's grouping by the day of completion belongs to the UI, since a completion timestamp becomes a day only in a time zone the core never has. Putting the manual list first inside a group is a property of every view, so it is stated once under the table instead of in one view's row, and the spec now says what dragging a task from one group into another means: it sets the field the view groups by, which is defined for every group key the core has except the tag, where a task carries a set of them and no single field would be set.
- `docs/process.md` section 7 and the new `docs/plans/TEMPLATE.md` set the plan format: a plan fixes the tasks, their order and the interfaces between them, and carries code only where it already ran; a task section is 50 to 100 lines of goal, files, signatures, rules, tests and verified facts, and the owner reviews the task table and the interfaces. A shipped section is not rewritten; a departure is stated in the task's PR and fixed forward into the sections that depend on it. Measured on M1's first seven tasks: the task table and the constraints held unchanged, while the plan's code for the logic-heavy tasks was rewritten from half to all of it.
- `docs/style.md` collects the code rules the owner's reviews established, so a diff meets them before review; implementing and reviewing agents get it, and a rule a review sets twice is added there. `docs/process.md` section 6 makes the review pass by a second agent before every PR a rule, and sends open questions to chat or a PR thread instead of the PR body, where they went unanswered.
- `docs/process.md` and `CLAUDE.md` record when the full process document is read instead of the digest: only `CLAUDE.md` is in the engineer's context by default, so the document is opened before architectural work, a spec review or the close of an increment, and whenever the digest is thin. A rule is never written in the digest alone.
- `docs/process.md` and `CLAUDE.md` record how reactions triage review comments: the reaction is left by the comment's recipient, the engineer now reacts to the owner's comments as well, 👀 marks a thread that is still being argued, and only 👍 threads are implemented.
- ADR-0002 records what threads-off SQLite costs at startup: the mutex around the library's one-time initialization is compiled out with the rest, so `SQLiteKit` performs that initialization once before any connection opens and nothing outside it may call the C API.
- `docs/process.md` status set to Approved v1 after the owner's review.
- README, `CLAUDE.md`, the process document's M1 examples and the M1 milestone description follow ADR-0001.

### Fixed

- The task entity of `TodoCore` is `TodoTask`, not `Task`. An unqualified `Task` in a module that imports the core resolved to the entity and hid `_Concurrency.Task`, so every consumer that used structured concurrency would have had to qualify it; a test that spells `Task<Void, Never>` from a consumer's point of view now guards the name. `TaskID`, `TaskStatus`, `NewTask` and `TaskChange` keep their names, and the plan's later tasks name the new type (#42).
- A stamp at the end of the hybrid clock's range no longer aborts the process. `HybridClock` saturates at the largest stamp the encoding holds instead of borrowing a millisecond outside it, and pulls the wall-clock reading into that range as well, so neither a journal row, nor an operation from another device, nor a system clock set past the end of time can reach the initializer's precondition and kill every later edit on the device. What saturation costs is written in the type: at the ceiling stamps stop being unique, so last-write-wins falls back to the device-id tie-break. Opening a store no longer bounds its own journal scan against the same trap, so the rule lives in the clock alone, where a future `receive` from the transport meets it too.
