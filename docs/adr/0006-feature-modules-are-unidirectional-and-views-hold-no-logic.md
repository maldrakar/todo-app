# ADR-0006: Structure every feature as a module with unidirectional data flow, and give views no logic

- Status: Proposed
- Date: 2026-09-20
- Related: `docs/specs/feature-module-architecture.md` (approved 2026-09-20), #63, #67, #78, ADR-0001, ADR-0004
- Amended: 2026-10-03, after the owner's review of #78 (see the end)

## Context

The core of M1 stores, queries, searches and journals, and reports a `ChangeSet` after every commit; nothing puts it on a screen. The brief asks for the architecture of every feature module to be chosen before product work, and the product runs on iOS, macOS, iPadOS, watchOS and the web through WASM, with SwiftUI for most of the Apple interface, UIKit where performance needs it, and React likely on the web. Whatever a feature's logic is written in has to be tested on the host and on wasm32 before a web page exists, and whatever crosses to a view has to survive a wire. The discussion is in the spec's sections 1 to 4.

## Decision

A feature is a module in the shared core: a `final class` conforming to `FeatureModule`, holding a reference to the `Store` and private state, and exposing a value `Model` and a synchronous `send(Event) -> Output?`. `Model` is exactly what a view draws, with every decision made and every string about the data finished. `Event` is the one door: `.action(UserAction)` for what a view may send, each action named for the control and the gesture and never for the operation it triggers, and beside it the events of the world, `.changed(ChangeSet)` from the store, later the change of the day, of the locale, a sync result. `Output` is what the module asks its parent for because it cannot do it itself. `send` never throws: what the store refuses becomes part of the model. A module publishes nothing and subscribes to nothing; the fan-out of a `ChangeSet` lives in the composition root, and a host takes one event at a time, queueing what arrives while one is in flight. A module spells dates and numbers through a formatting service whose protocol is shared and whose implementation is the platform's, since the core has no ICU. Navigation is state in the root module: which screens are open is data in the root's model, a screen is a child module that asks through its output, the root creates it with the store and drops it when the screen closes, and the way back from the platform is an action of the root. The shape of that state once there is more than one screen, a flat stack in the root or nested ownership by the opener, where a modal's module lives, windows, deep links and restoration, is not decided here: it belongs to the navigation epic, #67, after M3, with real screens to try it on. A view renders a model and sends actions: it holds no condition over a domain value, every `if` in it is over a `Bool` or an optional of the model, it formats nothing, its own labels are its vocabulary localised by the platform, and it keeps only what is its own, scroll, focus, hover, the window size, a drag in progress.

Alternatives. Logic on the UI side of each platform lost because every feature would be written and tested twice and nothing would run on wasm32 before a web page exists. A pure reducer with the store reached through effects lost because the store is synchronous and local, and every read would become an effect plus an answering event. A module that subscribes to the store and pushes its model through a callback lost because it opens a second door and makes the model something that arrives rather than something returned. A coordinator service injected into modules lost because the set of screens would leave the model and could not be tested as a value. A unidirectional-data-flow library such as The Composable Architecture lost because it is a large dependency that would have to build for wasm32, for what is one function per module here.

## Consequences

Easier: a module's tests are a store in memory, a sequence of events and a model compared whole, on the host and on wasm32; the watch, the command line and the web get the same feature; a view that decides something shows in a diff as an `if` over a domain value, so the rule is reviewable; a screen's module lives exactly as long as it is in the model and nothing has to be unsubscribed; navigation state is a value, so restoring it and opening a deep link are its serialisation.

Harder: every keystroke is a round trip through the module, which holds only because the round trip is synchronous; every event rebuilds the root model and the UI diffs it, to be measured on the first large list; a change of the locale is an event and a rebuild rather than a redraw; every module carries four nested types.

Constrained: no feature target imports a UI framework; no `send` throws; no module subscribes to the store or navigates on its own; a `Codable` or any other wire conformance is added with the wire and not before; a view formats nothing. Reversing this decision means moving state and decisions into views or view models per platform, which is cheap for one module and a rewrite of every feature afterwards.

## Amendment, 2026-10-03

Made in the owner's review of #78, where one module first composed another. Two rules follow from the decision above without being written in it, and spec section 3 had stated the first the other way round. Both bind every module from M3 on.

1. **A parent never reads a child's model to learn a choice.** A `Model` is what the child's view draws, and nothing else. A parent carries a child's model into its own whole, for the view, and decides nothing in it. What the child chose, or asks its parent for, reaches the parent only as `Output`. The route this rules out was tried in #78: a `selection` field on the list's model, which the root read at launch. The owner turned it down because the model is the view's, and the list already reports what was chosen as its output `.selected`.
2. **A child's first choice is its answer to `.created`.** A module publishes nothing and answers only the events it is given, so a choice nobody made, such as the view a list starts on, needs an event to answer. The parent sends `.created` to each child it creates, once, right after creating it and before anything else, and the child answers with its starting choice, or with nothing when it has none to report. The parent handles that answer on the same line every later answer takes, so the first choice and a click reach it the same way, and it names no choice of its own. `.created` is an event of the world, beside `.changed`, and no view can send it. It is named for what happened to the module (owner's naming in #78): its parent created it, which is not yet the same as putting it on screen. Whether more events of this kind follow is not decided here.
