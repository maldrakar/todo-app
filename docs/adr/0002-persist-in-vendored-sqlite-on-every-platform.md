# ADR-0002: Persist the core's data in vendored SQLite on every platform

- Status: Accepted
- Date: 2026-09-11
- Amended: 2026-09-12, the initialization consequence in the last paragraph, found while writing #12, and 2026-10-27, the thread mode, for #98 (see the end)
- Related: `docs/specs/core-storage-and-search.md` (approved 2026-09-11), #4, #98, amends ADR-0001

## Context

The core needs one storage implementation for iOS, macOS, iPadOS, watchOS and the web, within ADR-0001: full Swift, standard library and FoundationEssentials, no ICU. Task notes are Markdown and can reach megabytes in total, so list queries must not load them, and search over titles and notes has to fold case and diacritics in Russian and English without ICU. The web target has no file system of its own; durability there goes through JavaScript. The discussion is in the spec's "Storage engine" and "Persistence per platform" sections.

## Decision

The core stores its data in SQLite compiled from the amalgamation as a C target of the package, with one version and one set of compile flags on every target: FTS5 on, threads, extension loading and deprecated APIs off. It is the only C dependency of the core and its only runtime dependency outside the standard library and FoundationEssentials, which amends the dependency rule of ADR-0001. On Apple platforms the database is a file in WAL mode at a path the platform supplies, one connection per process. On the web the database lives in memory: the page passes the bytes of the previous snapshot at open and the core restores them with `sqlite3_deserialize`; after changes the page asks for a snapshot through `sqlite3_serialize` and stores it in IndexedDB. Notes are the last column of the tasks table and list queries never read them. Search uses two FTS5 indexes maintained by triggers: `trigram` over titles for substring quick find and `unicode61` over notes for word and prefix search ranked by bm25.

Alternatives. State in memory with a snapshot and journal file in pure Swift lost because notes would be loaded for every list and Unicode-aware search would be hand-written. A repository port with SQLite on Apple and an own format on the web lost because every query and test would exist twice. The system SQLite on Apple platforms lost because it does not guarantee the trigram tokenizer with diacritic removal and would split behaviour between targets.

## Consequences

Easier: one code path and one test suite on the host and on wasm32; indexed queries and transactions; full-text search without ICU; the database file can be opened with standard tools; notes stay out of list queries by construction.

Harder: the web bundle grows by about half a megabyte after gzip, counted in the M1 size budget; the amalgamation is a large file in the repository that compiles once per clean build; the browser persists by whole-file snapshot, so a tab that dies before the delayed snapshot loses the last seconds of edits; a schema change is a migration.

Constrained: no system SQLite anywhere; every core query is SQL against this schema; the web target must supply the snapshot bridge. Threads off also compiles out the mutex with which SQLite serializes its own one-time initialization, so that ordering is the caller's to provide: two threads that reach `sqlite3_open_v2` before the library has finished initializing will race, and the loser skips initialization, receives `SQLITE_OK` and finds no VFS registered. `SQLiteKit` therefore runs `sqlite3_initialize` exactly once through a Swift global before it opens any connection, and nothing outside `SQLiteKit` may reach for the C API, because a second entry point opens the race again. The core itself stays single-threaded, so this is the only place where threads meet SQLite; the parallel test runner is what found it, as `no such vfs:` in about one full run in six (#12). Reversing this decision means rewriting the store, the search and the migrations against another engine and converting users' files; the operation journal of ADR-0003 would survive such a move, since it is engine-independent data.

## Amendment, 2026-10-27

Made for #98. The decision compiled SQLite with threads off, and the last paragraph held that the library's one-time initialization was the only place where threads meet SQLite, because the core stays single-threaded. The process is not: the host test runner opens connections on parallel threads, and some of SQLite's state belongs to the process rather than to a connection, the random-number generator from which FTS5 draws 16 bytes at every open, the status counters and the unix VFS's list of open files. Threads off compiled out the mutexes over that state as well. Two threads that draw from the generator at once can copy 64 bytes into the 16-byte field and damage the heap, which crashed about one full host run in a hundred on a Mac (signal 5, `memory corruption of free block`) and once in CI on Linux (signal 11 in `sqlite3Fts5AuxInit` under `fts5Init`, a fault that fits a damaged heap, PR #156). On a Mac, ThreadSanitizer reported 99 races in `SQLiteKitTests` and 20,346 and 20,837 in two runs of the whole package.

**SQLite is compiled in multi-thread mode, `SQLITE_THREADSAFE=2`, on every target.** Its mutexes guard the state of the process again, while a connection and what was prepared on it stay unguarded, which the wrapper's types already say: neither `Connection` nor `Statement` is `Sendable`. Serialized mode, `1`, lost because it adds a mutex to every call on a connection that is never shared. On wasm32 the same flag compiles against the single-threaded stubs of the pthread mutexes in WASI's libc, so the compile flags stay one set for every target. `SQLiteKit` keeps its one Swift global, read before any connection opens, because upstream still leaves two first checks outside every mutex, harmless by its account and races to ThreadSanitizer all the same: `sqlite3_initialize` reads whether the library is initialized before it takes a mutex, so the global still runs it once; and at every file open the unix VFS reads the process id it keeps to notice a fork, rewriting it and resetting the generator while it differs from the current one, so the global now also seeds the generator, which sets that id before any file opens and leaves every later access a read.

Consequences. Easier: connections on different threads are safe, so the host suite runs in parallel without a hazard to memory, and on a Mac `swift test --sanitize=thread` reports no race in the whole package. Harder: the release wasm bundle grows by 9,256 bytes after gzip; the host got no slower, since at 50,000 tasks the counts and the writes measured the same in both modes within the noise of six interleaved rounds. Constrained: nothing outside `SQLiteKit` reaches for the C API, now because a call that reached SQLite before the global was read would race on those two checks; the core itself stays single-threaded, and a connection and its statements are used from one isolation domain at a time.
