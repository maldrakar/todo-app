# ADR-0007: Keep feature modules in the root package as shared code, and every platform host in a package under `Apps/`

- Status: Accepted
- Date: 2026-09-20
- Related: `docs/specs/feature-module-architecture.md` (approved 2026-09-20), `docs/specs/navigation.md` (approved 2026-10-14), `docs/specs/navigation-state.md` (approved 2026-10-22), `docs/specs/lists-screen.md` (approved 2026-10-25), #63, #67, #100, #117, #142, #146, #151, #161, ADR-0001, ADR-0006, ADR-0009
- Amended: 2026-10-14, after the approval of the navigation spec, 2026-10-15, after the owner's review of #100, 2026-10-22, after the approval of the navigation state spec, 2026-10-26, after the owner's reviews of #151, 2026-10-27, in #146, and 2026-10-30, in #161 (see the end)

## Context

Feature modules (ADR-0006) are pure Swift and have to build and test wherever the core does, on the host, on wasm32 under WasmKit and against the Apple SDKs. The Apple app imports SwiftUI, which builds neither on the Linux job nor for wasm32, and `swift test` builds every target of a package, so one Apple target in the root package would break both checks M1 set up. The spec's section 6 holds the discussion.

## Decision

Everything that runs everywhere lives in the root package: `TodoCore`, the `FeatureModule` target holding the module protocols and nothing else, one SwiftPM target per feature module under `Sources/Features/`, the root module, and one test target per feature, all obeying ADR-0001: a feature imports `TodoCore`, the standard library and FoundationEssentials under the `canImport` guard, and nothing else, with the wasm build in CI as the enforcement. Children depend neither on each other nor on the root; the dependency graph is written in the manifest. Everything that runs on one platform lives in a package under `Apps/` that depends on the root by a local path: `Apps/Apple` holds the SwiftUI views, the host, the composition root and the executables, and the web host will live in `Apps/Web` in the same arrangement. The wasm size probe drives the root module, since a web client ships it with the core.

Alternatives. One package holding the Apple targets too lost because a SwiftUI import fails on the Linux job and under wasm32. One `TodoFeatures` target for every module lost because the boundary between features would hold by discipline instead of by the manifest.

## Consequences

Easier: `internal` means "inside this feature"; the Linux job and the WasmKit run pick new features up unchanged; the future Xcode project and the web host each sit beside the package they belong to.

Harder: two targets per feature in the manifest; `swift test` in `Apps/Apple` builds the root package's targets a second time into its own `.build`; the size ceiling moves whenever a module joins the probe.

Constrained: no UI import in the root package, ever; no feature target reaches another feature's internals; a platform package never holds logic that a module could hold. Reversing this decision is a move of files and manifest entries, cheap at any time.

## Amendment, 2026-10-14

Made with the approval of the navigation spec, `docs/specs/navigation.md`, section 4, which ADR-0009 records. The decision above gave the `FeatureModule` target the module protocols and nothing else. The shared form of a parent now lives beside them: the protocol of an addressed module and the generic seat a parent holds each child in, which create a child from a route with the store and so need `Store` and `StoreError`. The target therefore depends on `TodoCore`, which every feature depends on already, and holds what every parent needs and nothing of any one feature. The rest of the decision holds: one target per feature, children that depend neither on each other nor on the root, and the hosts under `Apps/`.

## Amendment, 2026-10-15

Made in the owner's review of #100, the pull request that built the shared form of a parent. The dependency on `TodoCore` that the amendment of 2026-10-14 gave the `FeatureModule` target is withdrawn. A seat is created by its parent with the way to make its child, a closure over the child's own `init` that takes the route and whatever that child needs, so the contract names no dependency, and a screen that needs none, or needs others than the store, needs nothing from it. A module's `init` is no longer a requirement of the contract; it stays where a screen that cannot read what it shows refuses to be made, and the seat throws what that refusal throws. The target holds the module protocols and the seat, and depends on nothing. The amendment of 2026-10-14 stays as it was written, and the rest of the decision holds.

## Amendment, 2026-10-22

Made with the approval of `docs/specs/navigation-state.md` (#117), which ADR-0009's amendment of the same day records. The amendment of 2026-10-15 left the `FeatureModule` target the module protocols and the seat. Beside them it now holds `ScreenStack`, the flat stack a flow holds the screens open over its base in, the id of an element of it, and the protocol of a flow's enum of screens: what every flow needs and nothing of any one screen. None of them names a screen, and the target still depends on nothing. The rest of the decision holds.

## Amendment, 2026-10-26

Made in the owner's reviews of #151, the pull request that built the look of the Lists screen for every screen after it (#142), the first, the second and the fourth in its threads and the third in chat. Section 9 of `docs/specs/lists-screen.md` put the look into `TodoAppleUI`, and the plan's first task built it there as SwiftUI constants. The owner's point was that nothing about the look is a platform's except turning it into pixels: the colours, the rule that shades a list's colour and the type are the same values on the web, and the decision above already says a platform package never holds logic that a shared module could hold.

The root package therefore holds two targets for the look. `DesignSystem` holds the design decisions: the colours, each a light and a dark shade, a component's own among them; the type as text styles, a weight and a face, so that it follows the size a person sets; the motion, each a curve, a duration and a delay; and the icons. Each is a static member or a case of its own type, the way SwiftUI has `Color.red`: `DesignSystem.Color.sidebar`, `DesignSystem.Color.Components.Tile.amber`, `DesignSystem.Font.count`, `DesignSystem.Animation.popover`, `DesignSystem.Icon.sun`. The target depends on nothing. `DesignSystemComponents` holds the models and logic of the components every platform draws from those decisions, a list's tile first. `TileModel` holds every visual parameter a platform needs to draw a tile: its colour, whose background and glyph colours a platform draws; its glyph's icon and weight; its sizes, which it takes from its caller; and its corners, circular as the canvas's `border-radius` draws them. It depends on `DesignSystem` alone. Both are built and tested on the host and on wasm32 like every target of the root package, and the wasm size probe links them once a module it drives builds a component.

Neither depends on `TodoCore`, because the look must not know the domain (the owner's second review). The design system names a list's colours and icons itself, by the names the store keeps for them, so the store's names and the design system's agree by raw value, and a root test holds them together: the eleven tile colours against the core's `TaskViewColor`, and the icons of the views the store seeds against the design system's.

A component's model knows no screen: a tile does not know whether it stands in a phone's tree or a Mac's sidebar (the owner's third review). The feature module that forms its screen's model forms the models of the components on it, so a feature module may import `DesignSystem` and `DesignSystemComponents` to build them, choosing the sizes, fonts and colours its screen calls for, which widens what the decision above lets a feature import. The store's names of a list's colour and icon are read as the design system's there, by raw value, in shared code, so no platform host repeats the reading. For the same reason a row's title is four plain fonts, among which the module chooses.

A component's colours are semantic colours at the level of the component (the owner's fourth review). The tile's are `DesignSystem.Color.Components.Tile`, each giving the tile's background and the colour of the glyph on it, and `DesignSystem.Color.Components` is the home of every later component's colours. The design system defines the tile's by the canvas's `paint` rule from eleven bases nothing outside it sees, the background the base at 15 % opacity in the light and 24 % in the dark and the glyph the base mixed toward the ink or toward white, so that they are the canvas's and not shades worked out by hand. A component's model takes only the colours its component may use, so `TileModel` takes the tile's colour and holds no colour logic: it is plain data. No value of the look is optional either: the icons have a case for the default glyph, `bullets`, and the feature module that builds a model picks `.stone` and `.bullets` for a colour or an icon whose name is missing or unknown, so a platform draws every value it is given and chooses no default of its own.

A platform package holds only the renderers that turn the design system's values into the platform's, on Apple initializers of `Color`, `Font`, `Animation` and `Image`, and the views that draw a component's model, such as `ListTile` for a `TileModel`; a view takes every colour, font and animation it draws with from the design system through them. The rest of the decision holds.

## Amendment, 2026-10-27

Made in #146, the plan's fifth task of the Lists screen, whose sidebar builds its rows' tiles and title fonts for the width class of its window (`docs/specs/lists-screen.md`, sections 8 and 9; the amendment of 2026-10-26). The class was the root's own type, `AppModule.Width`, since the root alone cut the window's layout by it; a child never imports the root, so the sidebar could not name it, and a second enum of the sidebar's with the same two cases, onto which the root mapped its own, would be the same value said twice (`docs/style.md`, "One shape everywhere it fits").

**The `FeatureModule` target also holds the width class of a window, `WindowWidth`, beside the stack and the seat.** It is what a window's view reports and what every module that lays its screen out by the window reads, the root and the sidebar first, and it names no screen. The root takes it and hands it to the sidebar, and there is no `AppModule.Width` left. The target still depends on nothing, and the rest of the decision holds.

## Amendment, 2026-10-30

Made in #161, the eighth task of the Lists screen's plan, at the owner's word of 2026-10-30. The plan's seventh task drew the phone's Lists screen in Apple views that held every design decision themselves: the sizes and gaps, the colours, the fonts, the glyphs, the words, the menus, the bar, the look of the drag, the picker and the confirmation. The amendment of 2026-10-26 had put the tile's every visual parameter in its model, and the rest stayed in the views, where the sidebar of the plan's ninth task and every later platform would have had to copy each decision, and could only drift from it.

**A component's model holds every value its platform needs to draw the component, and the platform decides only what is its own: its container, its gestures and the drag, scrolling, focus and Reduce Motion.** Each size, gap, radius and line is in points; each colour, font, icon, animation and shadow is a token of the design system; each word is finished, in English until the formatting service arrives; and each control's action is a value of its module's actions. `DesignSystemComponents` holds the models, the tile's and fourteen beside it, each plain data, `Equatable` and `Sendable`, generic over the action where it carries one, knowing no domain and no screen and depending on `DesignSystem` alone. The feature module that forms its screen's model builds them with its screen's numbers, as `TaskViewList` builds a list's row, an area's line, the bar, the look of the drag, the move picker and the confirmation, and the menus of each kind of row. `DesignSystem` gains the tokens they name: the chrome's glyphs, as icons beside the lists' and named for what they draw, the bold weight, three fonts, the colour on the accent, and the look's shadows.

A view reads the models and draws them. What remains its own is what only its platform has: on iOS the glass under the bar's controls, the sheet and the alert, the fades at the screen's edges, the long press and the drag with the block it lifts, the sideways scroll that pins a row's accessories and the scroll to a field that opens, focus, and Reduce Motion, which draws without every animation a model gives. Whether a control stands on the platform's container a model says with `ButtonModel.Fill.container`, and which container, the glass or a toolbar, is the platform's choice. A view may switch over three of the components' enums, every case drawn and no `default` (`docs/style.md`, "Views").

Two things stay with the view because a model cannot hold them: the actions a text field sends, the typed text among them, which is made from that text, and the drag, whose finger only the platform has; the drag's look is the model's. The rest of the decision holds.
