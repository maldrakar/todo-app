# ADR-0009: Make every screen a child of the screen that opened it, addressed by a route with one text form

- Status: Accepted
- Date: 2026-10-14
- Related: `docs/specs/navigation.md` (approved 2026-10-14), `docs/specs/navigation-state.md` (approved 2026-10-22), `docs/specs/lists-screen.md` (approved 2026-10-25), `docs/specs/list-screen.md` (approved 2026-11-01), #67, #100, #117, #138, #166, #182, #195, ADR-0004, ADR-0006, ADR-0007, ADR-0008
- Amended: 2026-10-22, after the approval of the navigation state spec, 2026-10-25, after the approval of the Lists screen spec, 2026-11-01, after the approval of the list screen spec, 2026-11-02, when a group opened as a screen stopped being a row (#182), and 2026-11-10, when a screen the stack drops started to hear it (#195) (see the end)

## Context

ADR-0006 made navigation state in the root module and deferred its mechanics to the navigation epic, #67, with real screens to try them on. M2 built the first pieces: a root holding one child, the sidebar, and a pane that is a placeholder, with the duties of a parent written out once in the root. The owner's one concern with the module architecture is the root growing into a god module as screens arrive; and links, restoration, more than one window on the Mac and the web's address bar all need an address for every screen that can be open. The brainstorm and the spec's sections 1 to 5 and 7 hold the discussion.

## Decision

Every screen is a child of the screen that opened it: the root holds the first screens and nothing below them, every screen holds the screens it opens, and the tree of live modules is the navigation state. The duties of a parent are written once beside the contract, in the `FeatureModule` target: a protocol for a routable module, which requires a `Route` with a head and a tail, a `var route` assembled from its state and its children's routes, and an `Event` that spells `.route(Route)`; a screen is made by its own `init` from its route and the dependencies it needs, which may refuse to make it; and a generic seat a parent holds a child in, which the parent creates with the way to make the child, so that the contract's target names no dependency (owner's review of #100), and which creates the child from a route, sends it `.created` and hands the answer back, compares heads on `.route` and keeps, replaces or drops the child, and gives the parent the child's route and model. A child its parent always has, such as a window's sidebar, is a field of the parent's state and not a seat: a seat makes, keeps, replaces and drops a child, and such a child needs none of the four (owner, 2026-10-16). A parent still writes per child its `Model` field, its `UserAction` case, one line forwarding the child's actions, one forwarding `.changed`, and its reaction to the child's `Output` in a `switch` with no `default`. Inside a module, navigation has one entrance, apply a route: a tap, a link, a relaunch and the way back are each a route applied, and applying is a reconciliation by head and never a rebuild, so session state survives what did not change; the head of a live module never changes, and a module that receives `.route` looks at the tail alone. A route is a plain value and not a model; it may carry what a screen opens with, in its tail and never in its head, read once in the screen's `init` and never written back, and it carries no session state. It has one text form, a path with a query written and read by one codec in the core, which is the deep link, the state a window is restored from and the web's route; the composition root strips the platform's wrapping, a scheme or a site, and reads the string with the codec, and a string that does not read is refused with a typed error naming the segment. A request a parent cannot serve, it re-emits as an output of its own, under its own name. A window is a tree of modules with its own root and its own host, and a process is one store and one composition root that creates a host per window and hands every `ChangeSet` to every live host, under the rule that a module never writes to the store in answer to `.changed`; whether an idle host takes the change set inside the other window's event, which the spec chooses, or on the next turn of the main actor is the plan's probe to settle. The root's first output to the platform is `.openWindow(Route)`, so the host's output is no longer `Never`. Quick entry is the root's child on every platform; whether a child is drawn pushed, in a column or in a sheet is rendering, and no SwiftUI container reaches the core or an ADR. The names of the protocol and the seat are settled by a compiler probe against SwiftUI and Foundation before any task uses them.

Alternatives. A flat `path` of screens in the root with modals beside it lost because the root would grow with every screen and hold the transition table of the whole app, and the core would have to tell a push from a modal. A coordinator service modules call to navigate lost, as in ADR-0006, because the set of open screens would leave the model. Navigation in the views with `NavigationLink` and `@State` lost because a view deciding what opens is a view holding logic, and none of it runs on wasm32. One root per process holding every window in a table lost because every action and model would carry a window id and iPhone would carry the table for its one window. Quick entry as a window of its own on the Mac lost because the module's home would depend on the platform. Text routes handled inside modules lost because every module would parse, and a typo would be found at runtime. A `Codable` route lost because it is a second serialisation beside the text form, with no test on wasm32 and with a conformance ADR-0006 says comes with the wire; the window's value is the text form. The view parsing the URL it receives lost because a parser in a view is logic in a view, and it would exist once per platform. The child's model as the navigation item lost because SwiftUI hashes the item and a model has hundreds of rows. Replacing the module tree on every `.route` lost because a link into an open task would lose the session state of everything on the way.

## Consequences

Easier: every screen is addressable by construction, since a routable module cannot exist without a route; a deep link, restoration after a relaunch and the web's address bar are one codec and one entrance, tested on the host and on wasm32 before any platform draws; a parent's code per child is a handful of lines and the root does not grow when a grandchild learns a new screen; a second window on the Mac and the one window of iPhone are the same code; a tap and a link cannot open different things because they are the same code.

Harder: every routable module carries a route type and its reconciliation, which is a type and a few lines per screen; the fan-out of a change set to every window rests on a rule that nothing enforces but a test; every parent forwards each event of the world in a line of its own, until a third such event may fold them into one case, which the spec leaves open; a route that names a gone entity has to be answered with what still exists and a sentence, screen by screen.

Constrained: no module navigates except by applying a route, and no view sends one or parses a URL; no module writes to the store in answer to `.changed`; the text form is the only serialisation of navigation state, and session state never enters it; a window is one host and one root, and the store is one per process; a parent learns a child's choice only through its output, as ADR-0006 already requires. Reversing this decision means flattening the tree back into the root, which is cheap for the three screens of this epic and a rewrite of every parent afterwards.

## Amendment, 2026-10-22

Made with the approval of `docs/specs/navigation-state.md` (#117). The owner reopened navigation before closing M3 because the root view assembled the stack's path from the window's route, and so knew the tree of modules: that the sidebar holds the list and the list holds the task. The title holds: the screen that opens another still decides it and still hears its `Output`. What changes is who holds the opened screen, how a screen opens and closes, and what the core knows of a push. The spec's sections 1 to 5 hold the discussion. `ScreenStack` and the slot's two cases are the owner's names; `.wentBack(to:)` and the id of an element are working names, settled by the plan's compiler probe as the decision settles its names.

1. **The opener declares what is open over it, in one slot of its own state.** The slot is an optional enum with two cases, `pushed` and `presented`: it holds nothing, a pushed screen or a modal, never two at once, since the platform shows one thing directly over a screen (owner, in review). Either case holds the route of the screen opened there, whole, as the opener declared it. A tap fills the slot, Back empties it, and nobody but the screen writes it; when subtask B opens subtask A, B decides. A slot is part of the screen's route, so it is read as a parent reads a route, and never a model. The decision's "whether a child is drawn pushed, in a column or in a sheet is rendering" changes: the core now tells a push from a modal, since the opener says which it declares, and a column from a path, since the module decides the layout (ADR-0006, amendment of 2026-10-22). No SwiftUI container reaches the core still.
2. **A flow holds the screens open over its base flat, in a `ScreenStack`, and an opener no longer holds what it opened.** A flow is a base screen and the screens open over it. A window's flow belongs to the window's root, `AppModule`, the flow's owner: the base is the sidebar, a field of the root as before, and the screens over it stand in a `ScreenStack`, a generic value in the `FeatureModule` target beside the seat, ordered up from the base. A modal with screens of its own is a flow too (point 5). After every event the stack walks up from the base and reconciles each slot with what stands above it by the seat's rule: the same head keeps the screen with its session state; another head makes the declared screen, tells it it was created and replaces everything above; an empty slot, or a modal, drops everything above. A screen that cannot be made leaves what was open, and its opener is told why and takes back what stays open. A slot written again with the head it already holds is a new declaration, handed once to the screen it keeps. The stack sends `.created` to a screen it makes, and the answer, like every later `Output` of that screen, goes to the screen right below it, which is its opener; the base answers the flow's owner. So an opener hears everything the screen it opened asks for without holding it. Each element has an id the stack hands out, which gives the view a stable identity and lets the same kind of screen stand twice, a task over a task, and which is never written into the text form. The flow's owner declares one enum of the kinds of screen its stack can hold, whose mappings decide nothing. The lines the decision has a parent write per child, its `Model` field, its `UserAction` case and the forwarding of its actions and of `.changed`, move into that enum, and the opener keeps only its reaction to the child's `Output`. So the decision's "every screen holds the screens it opens, and the tree of live modules is the navigation state" becomes: every screen declares the screen it opens, and the declarations are the navigation state, which the stack follows. The seat stays for a child a parent holds alone, the window's quick entry.
3. **The root holds every screen of its window's stack, and decides none of its transitions.** The decision's "the root holds the first screens and nothing below them" changes: the root, as the owner of its window's flow, holds the stack and every screen in it, and its enum gains a case for each kind of screen that can stand in a window. It still never learns which screen opens which, since that stays in the openers' slots, so the owner's concern, a root grown into a god module holding the transitions of the whole app, is answered as the decision answered it. The decision's "the root does not grow when a grandchild learns a new screen" holds for transitions and not for kinds: a new kind of screen is one case in the root's enum, and a new transition between kinds the enum has is nothing in the root.
4. **The way back is an event of its own, and navigation is a write of a slot.** SwiftUI reports a pop only as a shorter path, from its back button, the swipe from the edge, or the long-press menu that can go back several screens at once. The view sends that path whole, as the window's action `.wentBack(to:)`; the flow tells the screen now on top that what was over it was closed, and that screen empties its slot and cannot keep it. A path naming a prefix the stack does not hold moves nothing. So the decision's "inside a module, navigation has one entrance, apply a route", with a tap, a link, a relaunch and the way back each a route applied, becomes: inside a module, navigation is a write of its own slot, by its own gesture, by Back, or by `.route` for a link and a relaunch, and the stack's walk after the event is the one reconciliation for all of them. The constraint "no module navigates except by applying a route" becomes "no module navigates except by writing its slot".
5. **A modal is a flow of its own, declared the same way.** A screen declares it in the slot's `presented` case. Its base is the declared screen, its own stack holds what is pushed inside it with the same walk, recursively, and what its base answers reaches the screen that declared it. A flow shows one modal at a time, and a modal goes when the screen that declared it leaves the stack. The window's root is the flow's owner and not a screen of its stack, so it pushes nothing; it declares quick entry in a slot of its own that holds only a modal, and quick entry stays the root's child. A screen's modal and a modal with a stack are built when a screen first needs one.
6. **The window's route keeps its shape and its text form.** The route of a window is the chain of its screens' routes. A link writes the base's slot, and the stack hands each screen it makes or keeps its part of the route; the other way, the root writes the route down from the stack, each slot replaced by the route of the screen that actually stands over it, so a declaration that has aged never reaches the text. The codec, its text form and its tests do not change.

Alternatives. Keeping the tree, B holding A in a seat, and projecting it into a path in the model lost: B hears A's answers without holding A, and projecting a tree into a path is the glue moved from the view one layer down. Commands, an opener telling a router to push, lost because a command is a one-shot that a link or a relaunch would have to replay, and the stack could drift from what the screens think is open; a slot is state, and the stack always follows it. A path of routes with no ids lost because the same screen could not stand twice, and the view would search for an element's model. Two slots per screen, a push and a modal at once, lost because the platform shows one thing over a screen. The first alternative above, a flat path in the root with modals beside it, still loses, and so does its form of 2026-10-21, the root deciding what is pushed: there the root decided every push and held the transition table of the app, and here the root holds the screens and the openers decide. Its other reason, that the core would tell a push from a modal, is accepted now, since an opener has to say which it declares.

Consequences. Easier: the view binds a path the model gives it and knows no tree; a subtask is a slot on the task screen and one more element of a kind the stack already holds, with no level in any view; an opener hears what it opened without holding it; a screen's whole navigation is one value in its state. Harder: the root's enum gains a case and a line per mapping for every kind of screen a window can hold, compiler-checked with no `default`; the stack and its walk are a generic value with tests of their own; in a wide window a screen that opens a modal closes what is pushed over it, which no screen does today; a new tree of views, a third column, say, is a new case of the module's layout shape and no longer a change inside the Apple package alone. Constrained: a screen says what is open over it only in its slot, and no module creates, holds or drops a screen of its flow's stack but the stack; no view composes a path, or reads the route to decide what to draw. Reversing this amendment means giving each opener back a seat for the screen it opens and the view back a path built from the route, which is cheap while three kinds of screen stand in a window and grows with every kind after.

## Amendment, 2026-10-25

Made with the approval of `docs/specs/lists-screen.md` (#138), whose section 5 holds the discussion. The Lists screen asks before it deletes and offers a picker for Move to…, and the question was whether a dialog is a screen the opener declares in its slot. It is not.

**A dialog over a screen, with no subject and no stack, is that screen's state, drawn from its model; a screen with a subject is declared in the slot.** A confirmation and a picker have no subject of their own, no address a link could name and nothing a relaunch should restore, so they live in the module's state beside its other session state, the model carries each as an optional, and the view draws it as an alert or a sheet while the optional holds a value. The slot keeps its meaning from the amendment of 2026-10-22: it holds a push or a modal, never both, and a dialog declared there would close what is pushed over the screen, the list open beside the sidebar on the Mac. The test for which is which: a screen has a subject, an id in its route, and can stand in a stack; a dialog has neither.

Consequences. Easier: a dialog is two optionals and two actions away, with no case in the root's enum and no route. Harder: a module with dialogs has more session state that a relaunch loses, which is accepted since a half-finished confirmation is nothing to restore. Constrained: no dialog in a slot, and no screen with a subject drawn from a model's optional.

## Amendment, 2026-11-01

Made with the approval of `docs/specs/list-screen.md` (#166), whose sections 2, 3 and 9 hold the discussion. The list screen opens a block as a screen of its own, a list inside the list or the view of one of its groups, and opens a task in place as a card with the full screen a button away.

1. **A list may declare a list over itself, by the view's id, as every list is addressed.** `TaskList.Route`'s head stays the view's id, and its tail becomes an enum of two cases, the task screen or another list, each holding that screen's route whole, so that `view/a/view/b/task/t` is list b open over list a with task t over b. A group opened as a view is a list over its list, since a group is a view of its own with an id (ADR-0004, amendment of 2026-11-01), and needs no word of its own in the text form; superseded by the amendment of 2026-11-02, which gives a group an address of its own after its list's. The same kind of screen stands twice in a stack, which the stack's ids were made for (amendment of 2026-10-22, point 2) and which no screen had done. The sidebar's highlight stays on the list it declared, the base of the chain.
2. **A task opened in place is the list's state and not a screen.** The card is a row grown: it has the list's subject and no address of its own, so by the test of the amendment of 2026-10-25 it is state, drawn from the list's model as an optional, and never a slot's content. The list's `task/<id>` tail keeps M3's meaning, the task screen pushed over the list, which Open full screen declares; a link to a task opens the task screen, and a relaunch opens the list with no card, which is accepted.

Consequences. Easier: one more case in one route's tail and no new kind of screen in the root's enum; a group's screen is the list screen on another route. Harder: the first chain of two screens of one kind in a stack, exercised by tests the stack never had. Constrained: the card never enters the route; a list over a list is declared by the view's id and nothing else, and a group over its list by the list's id and the group's key since the amendment of 2026-11-02.

## Amendment, 2026-11-02

Made with #182, on the owner's decision in chat (2026-11-02). A group opened as a screen is no longer a view with a row and an id of its own but a view the module derives from its list and the group (ADR-0004, amendment of 2026-11-02), so it can no longer be addressed by a view's id, as point 1 of the amendment of 2026-11-01 had it. This amendment gives it an address of its own.

**A list may declare one of its own groups over itself, addressed by the list's id and the group's key, with a word per grouping that is known in advance.** The head of the list's route becomes the view's id and, on a group's screen, the group's key, so a group's screen and its list's have different heads and the stack pushes the one over the other; the same group of the same list declared again keeps its screen and its session state, and a group by day keeps its screen across midnight, since its key is a distance and not a date, while the screen reads its page for the new day. In the text form a group stands after its list's `view/<id>`, one word naming the grouping and one segment naming the key:

| Grouping | Address of a group |
| -------- | ------------------ |
| by the day of When | `day/<distance>`, `day/none` |
| by the day of the deadline | `deadline/<distance>`, `deadline/none` |
| by tag | `tag/<id>`, `tag/none` |
| by parent | `parent/<id>`, `parent/none` |
| by status | `status/open`, `status/done`, `status/canceled` |

A distance is a count of days from today, signed, `0` today, `+1` tomorrow, `-2` two days ago, and never a date, so a link and a restored window keep meaning "tomorrow" as Today's address keeps meaning today. So `view/a/day/+1` is list a with its group of tomorrow over it, and `view/a/day/+1/task/t` that group with task t over it. A group holds no lists, so after a group only the task screen's part may follow. The codec reads the words as it reads the rest of the path and refuses, with the typed error naming the segment, a word it does not know, a key that does not read and a distance a day cannot hold. A group that reads but names nothing, a word that is not its list's grouping or a tag or a parent that is gone, is refused when its screen is made, as a list that names a gone view is: what still exists stays open, here the list, and the list says why. Each address is written and read with no read of the store.

Consequences. Easier: a group's address is known before anything is read or written, a link to one can be written by hand, and opening or restoring one writes nothing; a group's screen is the list screen on a route with a group in its head. Harder: the codec gains five words, each with its key's syntax and its refusals, tested on the host and on wasm32, which the amendment of 2026-10-22, point 6, did not foresee when it said the text form would not change; a list's route has a head of two parts; a link to a group can outlive the grouping it names, and is refused then. Constrained: a group is declared only over its own list and holds only the task screen over itself; a group's key in the text form is never a date. Reversing this amendment means giving a group a row and an id again (ADR-0004, amendment of 2026-11-01, point 3) and addressing it by them.

## Amendment, 2026-11-10

Made with #195, on the owner's decision in chat (2026-11-09 and 2026-11-10). The way back of point 4 of the amendment of 2026-10-22 told only the screen now on top, and the drops of its point 2, an empty slot and another head, told nobody, so a screen the stack let go heard nothing of it. A list's open card keeps what is typed in it as session state, written on Return, on a lost focus or when the card closes, and a new task with nothing put in it is deleted when its card closes. The list's own back button closes the card before it answers; the edge swipe on iPhone, the Mac's toolbar back, a pop of several screens by the long-press menu of a task screen's back on iPhone and the iPad, another list chosen in a wide window's sidebar and a link let the list go with what was typed unwritten and the empty task kept, the field's lost focus arriving afterwards for an id the stack no longer held.

**Every screen the stack drops, by any path, hears one last notice before it goes, and closes what it has open by the rule of every close.** The stack hands `StackNotice.dropped` to every element it lets go, by the way back, by an opener emptying its slot and by an opener declaring another head, top down, the topmost first, each before it goes. On the way back the dropped screens hear it before the screen now on top is told that what was over it was closed; when another head is declared the new screen is made first, so a screen that cannot be made drops nothing and nobody hears it. A list closes what it has open as its back button does: a new list's name being typed is settled and the card closed, what was typed written and a new task with nothing in it deleted. A write the store refuses is not said, since no screen is left to say it on. What a dropped screen answers is handed to nobody, neither to its opener nor out of the call: its opener goes with it, or is the one that emptied or rewrote its slot. So point 4's "the flow tells the screen now on top that what was over it was closed" becomes: the flow tells every screen it drops that it goes, top down, and then the screen now on top; and the drops of point 2 let each screen go with the same notice.

**A drop in a call that hands a change the store committed hears nothing.** No module writes in answer to `.changed`, and the fan-out of a change to every window rests on it: a write there would start a fan-out inside another, and a third window would take the second change before the first. So the owner's enum of screens says which of its events, the base's and an element's, are changes (`StackScreen.isChange`), a `switch` with no `default`, and a call that hands one lets its screens go as before, unheard. Text typed and not yet written in a list a change deleted, or in a group's screen whose group a change took, or in a screen standing over either, is lost, which the owner accepted. The way back is never a change.

Alternatives. The view sending a field's lost focus before the path lost: the order of a lost focus and the path's write is not SwiftUI's to promise, and a lost focus does not delete a new task with nothing in it. The root sending the list's own back action for it lost: the root would decide for a list what a gesture means to it. The dropped screens writing in answer to `.changed` too lost: a write in answer to a change starts a fan-out inside another.

Consequences. Easier: a screen closes what it has open however it goes, in one place, and the way back and every other drop are one road for it; a screen that learns to hold something open learns to close it there. Harder: the owner's enum says which of its events are changes, in two `switch`es, and maps one more notice per kind of screen; a screen made in place of others reads the store before they close what they have open, so it shows their writes only after the change those writes commit, which the host hands the window after the event and before anything is drawn; a dropped list reads its page once more after its last write, which nothing draws. Constrained: nothing a dropped screen answers reaches anyone, so a screen cannot ask for anything as it goes; a screen dropped in a call that hands a change writes nothing, and what it held unwritten is lost. Reversing this amendment means letting screens go unheard again, and a list's typed text lost on every way back but its own button.
